# Platform layer: OS-specific code in one crate

All code that needs an API existing on one operating system only lives in the `oxide-platform` crate, with one implementation per OS behind the same functions. Everything else in the workspace is identical on every OS. A local check, also run in CI, enforces it.

## Background and problem

Most contributors, people and agents alike, work on macOS. Windows-only code is never compiled on their machines, so a mistake in it (a type used only in a Windows branch and never imported, a trait method called without its trait in scope, an import used only by Unix code that becomes "unused", a hard error under the workspace lints) shows up when CI runs, 10 to 17 minutes after a push. From 13 to 18 November, 16 of the 24 failed CI jobs were such errors, for example in #495 and #511. A Mac compiler removes the Windows branches before checking them, so no local lint could see them. The cause was structural: about 206 OS-specific conditional compilation points across 35 files, mixed into shared code that shared its imports and helpers.

## Decision

- **One crate.** `crates/oxide-platform` is the only place with an OS conditional-compilation attribute (`#[cfg(windows)]`, `unix`, `target_os`, `target_family`, also under `not`, `all`, `any` and `cfg_attr`) or a direct use of an OS-only API (`std::os::{unix,windows,..}`, `libc`, `windows-sys`, `objc2*`, `sysinfo`). It is also the only crate whose `Cargo.toml` names an OS binding crate.
- **One implementation per OS.** `src/macos/`, `src/linux/` and `src/windows/` each offer the same modules (`fs`, `process`, `system`, `terminal`) with the same public items and signatures. `src/lib.rs` picks the one for the OS, once; no `cfg` attribute appears inside an implementation. macOS and Linux share the POSIX code in `src/posix/` by re-exporting it (`pub use crate::posix::<module>::*;`). Code that is the same on every OS but that the implementations need (`command`, `diag`, `sync`, `registry`) sits next to them, because this crate depends on no other Oxide crate; `oxide-provider` re-exports `diag`, `sync`, `command::{os_command, os_tool, resolved_command}` and `process`, so Core and the app keep their imports.
- **The expression form for values.** A difference that is only a value (a shell name, a flag, a suffix, a command to run) is written `if cfg!(windows) { .. } else { .. }` anywhere in the workspace: every OS compiles and type-checks both branches, so a Mac compiler sees the Windows branch. If a branch needs an OS-only API, it is a new function in the platform layer instead.
- **A ratchet, not a big bang.** `tools/checks/platform-layer.mjs` fails when a file outside the platform layer and `crates/*/tests/support/` has an OS-specific attribute or API. Violations that existed on 18 November are recorded per file in `tools/checks/platform-layer-baseline.json`. A new file, or a higher count in a listed file, fails the check; a lower count fails it too, until `node tools/checks/platform-layer.mjs --write-baseline` lowers the entry (that command refuses to raise one). Lowering is a normal diff in a PR.
- **Parity.** The same script fails when one implementation lacks a public item another offers, or offers it with a different signature (parameter names compare without a leading `_`).
- **Contract tests.** `crates/oxide-platform/tests/` holds tests that run unchanged on the macOS, Windows and Linux lanes. A per-OS input is a value picked with the expression form. Integration tests of other crates take per-OS inputs from `tests/support/` helpers and gain no OS-specific conditional code.
- **Windows check on any OS.** `node tools/check.mjs windows`, on macOS or Linux, runs `cargo xwin clippy --target x86_64-pc-windows-msvc --workspace --exclude oxide-app --all-targets -- -D warnings`. It needs `cargo install --locked cargo-xwin` (which fetches the Windows SDK headers that C dependencies such as `ring` need) and LLVM's `llvm-lib` (`brew install llvm`). `oxide-app` is left out because its Tauri build script needs `llvm-rc`; its OS-specific code is in the platform layer, which the check covers. The runner sets `RUSTFLAGS=-Cdebuginfo=0` unless it is set, because cargo-xwin cannot read the linker flag with spaces in `.cargo/config.toml`, and that flag only matters when linking. When it passes, it stamps the hash of `crates/oxide-platform/src/windows/`; the full `node tools/check.mjs` on a non-Windows OS prints a notice when that directory differs from `origin/main` and the stamp does not match.

## Limits

A text check does not see a macro that expands to an OS attribute, or an OS API reached through a re-export under another name. Those are left to review and to the CI Windows lane. The Windows check does not build `oxide-app`.

## Consequences

- A contributor adding a capability that needs an OS-only API adds one function to each of `macos/`, `linux/` and `windows/` (or to `posix/` for the two Unix ones) and calls it with no conditional code around it.
- The failure message names the file and line, says OS-only code belongs in `crates/oxide-platform`, and points to the expression form.
- The migrated areas are process supervision (process groups and Job Objects, termination, the live-process registry, private file writes, console handling, `command` helpers), terminal and PTY handling (shell launch, block scripts, Ctrl+C, shutdown, completion) and native system integration (activity assertions, opening URLs and files, the Dock icon). The baseline fell from 337 to 147 uses (counting each attribute and each OS-API line). What remains (updates, the agent reporter socket, language installers, tests that create symlinks or file modes, the macOS-only Dock reopen event) shrinks through the baseline.
- ADR-0016's rules hold after the move: the guarded signal helper (`posix/signal.rs`), `os_command` and `resolved_command`, the poisoning-recovering `lock_recover` and `diag::best_effort` each still have one implementation; the old module re-exports it. Every `unsafe` block moved with its `SAFETY` comment.
